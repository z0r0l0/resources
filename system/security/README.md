# 🔐 权限审计方法论

> 回答一个问题：**这个账户在这台机器上实际能做什么？**
> 本文只讲方法，不含任何具体主机的结果（结果在私有仓库保存）。

---

## 核心原则：测量，绝不推断

每一条权限结论都必须能追溯到本次实际运行过的命令。

**真实教训。** 曾经这样推理：「`sudo -n` 要密码，所以 root 这条路是关闭的，
权限上限就是 `docker` 组。」这个结论被当成事实报告了出去，**它是错的**——
sudo 密码就存在一个可读的密钥文件里。推断产生了一个自信且错误的结论，
最后不得不向用户撤回。

给每条结论标注 **实测** 或 **未验证**，绝不让两者混在一起。
未验证就写未验证，不要用「大概率」填空。

---

## 审计七步

| # | 步骤 | 命令要点 |
|---|------|----------|
| 1 | **身份与提权** | `id`、`sudo -n true`，**并检查可读的密钥文件里是否就有提权凭据** |
| 2 | **危险用户组** | `id -nG`：`docker`/`lxd` = 等效 root；`disk` = 裸设备；`shadow` = 读 `/etc/shadow` |
| 3 | **文件系统写入范围** | 临时文件**建完即删**逐个试探；**挂载点根目录与用户子目录要分开测** |
| 4 | **凭据可读面** | 只列**文件名与键名**，永不打印值。这是全场信号最强的一项 |
| 5 | **自我改写区** | 配置、人格文件、技能、记忆、定时任务、钩子——改动无即时症状，但决定未来行为 |
| 6 | **网络出口** | 代理端口是否可达、逐域名可达性（**不对称本身就是信号**） |
| 7 | **对外触达通道** | 通道目录、定时任务、配对设备——「能对谁说话」比文件权限更能界定影响半径 |

---

## 第 3 步的陷阱：盘根 ≠ 用户目录

这是实际踩过的坑。在 WSL 上：

- `/mnt/c`（Windows 系统盘**根**）→ **只读**（Windows 对系统盘根设了 ACL）
- `/mnt/c/Users/<user>` 及其子目录 → **可写**（9p 挂载带 `uid=<uid>;gid=<gid>`，无 ACL 检查）

只测了用户子目录就写下「C: 可写」，是过度断言。**两者必须分行记录。**

## 第 4 步的纪律

```
✅ 正确：密钥文件可读，其中含提权凭据（键名：<KEY_NAME>）
❌ 错误：把该凭据的值写进任何文档、日志、提交或记忆
```

列键名用 `grep -oE '^[A-Za-z_][A-Za-z0-9_]*' <file>`。
**审计报告、提交信息、终端输出里都不应出现值本身。**

---

## 发布前：三道验证

审计结果若要落盘到版本库，发布前必须过：

| 验证 | 做法 |
|------|------|
| **泄漏自查** | 用密钥文件里的每个值去搜待发布文件，命中即中止。写完「存在键 X」是对的，写下值不是 |
| **独立回读** | `git ls-remote` 比对提交号，再从远端读回文件比对内容与行数。「推送成功」不是证据 |
| **脱敏复核** | 账户名、内网地址、标识符是否已替换为占位符 |

## 自动化

本仓库的私有伴生仓库中附有探针脚本，可一次性跑完上述七步：

```bash
bash permission-probe.sh [proxy_url] [secrets_file]
```

性质：只打印键名不打印值；写入测试自带 `trap` 清理；通道 ID 自动打码；
可重复执行无残留。

## 报告风格

面对用户输出时：**先纠错，再报新发现**。如果有此前的结论被推翻，
在给出新结论之前先明确撤回。每条标注实测/未验证。
结尾给编号的决策清单（哪些风险接受、哪些关闭），
**不要单方面修改安全敏感设置**。

---

## 判断边界

真正拦住一个 Agent 的往往不是文件权限，而是：

1. **人类确认门** —— 高风险调用需要用户批准
2. **凭据不可得** —— 提权密码不在可读范围内
3. **对外通道受限** —— 只能对特定对象说话

第 1 条最容易被忽略，也最容易失效：它依赖于人真的在看。
