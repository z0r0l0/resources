# 📓 复盘：Hermes 桌面运维面板（维尼）· 2026-10

> 一次从"能用"到"无人值守 + 可维护"的完整迭代复盘。
> 记录做了什么、数据是多少、以及**哪些弯路本该避免**。

---

## 一、起点与目标

起点是一个刚跑通的 Hermes Agent（QQ 网关 + 定时任务），痛点是：

- **看不见**：网关活没活、通道通不通、内存水位多少，只能翻日志
- **够不着**：想改一条记忆、停一个技能、加一个提醒，都得进终端敲命令
- **不自愈**：进程卡住没人管；机器重启后能不能自己回来，没有判据

目标：做一个**自己的运维面板**（桌面端插件 + FastAPI 后端），把日常操作面板化，
并让"机器出问题"这件事**自己喊出声**。

## 四、弯路与教训（这部分比成果更重要）

### 1. 误判"没启用"：`static` 不等于"没跑"

看到看护器 `is-enabled=static`、`is-active=inactive`，我第一反应是"根本没在跑"。
**错。** 它们是 oneshot，由各自的 timer 拉起，跑完即退 —— static 是正常的。
正确姿势是看 **timer 的 NEXT/LAST**，并确认 `Type=oneshot`。

### 2. 误判"卡顿"：重启期抖动 ≠ GIL 泄漏

日志出现 `event loop stalled 85.1s` 很吓人。但线程栈显示**所有线程都在等队列**
（`queue.get` / `waiter.acquire`），没有任何业务线程占 GIL；且时间戳正好对上"我 kill 应用"的瞬间。
结论：**关闭/启动期的正常抖动**。

口诀：卡顿**时长 + 线程栈 + 发生时刻**三者一起看，只看时长必然误诊。

### 3. 排查要先问清"哪个 X"

用户报"视图打不开"。我先去查数据加载、渲染、面板尺寸 —— 全是弯路。
追问后才知道："整篇和逐条可以打开，**视图**打不开"。
真相：`视图　整篇　逐条` 里"视图"只是灰色说明文字，不是按钮。

**教训**：报障先问"具体哪个元素、点什么、期望什么、实际什么"。另外，
**UI 上不要放看起来像按钮的纯文字**。

### 4. 别靠读代码推演布局问题，直接量

区块宽只有 59px。与其推演，不如读 `getComputedStyle(el).flexBasis`（看到 `"0%"` 而非期望值），
再注入一条 CSS 验证假设（宽度立刻恢复到 393px）—— 一次实验锁定根因：
`flex-1` 是简写，把 `flex-basis` 归零并覆盖了后面的 `basis-[...]`。

### 5. 测试自己也会骗你

- 断言只换了 `MEMORY_DIR`，却没换**导入时算好的** `MEMORY_BACKUP_DIR` → 备份飞进**真实**目录。
  （教训：派生常量要一起替换；补一条"真实目录未被污染"的断言守着。）
- 断言写"暂停后周视图仍可见"，却用了**一年后**的时间点 —— 那本来就不在 7 天窗口里，
  是个**假命题**。换成"2 天后"才成立。
- 静态断言永远是绿的 → 必须做**反向对照**（把正确写法改回错误的，断言要能红）。

### 6. 交付的定义要往下压一层

"单元执行成功"≠"消息发出去了"。退出码 0、`Result=success` 都可能掩盖"里面的 `hermes send` 失败"。
所以开机报平安的验收**必须去日志里核对**"本次开机之后是否真有成功记录"。

## 五、沉淀

这个项目真正的产出不是那个面板，而是三条**可迁移**的做事方式：

1. **让故障自己喊出声**，而不是等人去看。—— "该来的没来"本身就是信号。
2. **每一层都验到"真的发生了"**：单元状态 → 单元执行 → 日志事实 → 实机交互。
3. **能红才算有效**：任何断言、任何检查，都要能证明它在出错时会报错。
